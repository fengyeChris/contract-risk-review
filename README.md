# 合同风险审查系统

输入一份英文合同，输出站在**买方/客户立场**的风险报告：10 类关键条款哪些在、哪些压根没写、有没有坑。每条都给出中文理由，以及**原文里是哪一句**（带精确字符位置）。

在 CUAD 的 198 份公开合同上（有第三方人工标注的标准答案）：

| 指标 | 结果 |
|---|---|
| 存在性 F1 | **0.878**（精确率 0.873 / 召回率 0.884，微平均） |
| 证据定位准确率 | **0.924**（引用位置与标准答案的区间重叠） |
| 必备条款缺失识别 | **0.928**（责任上限、知识产权、适用法律三类该报警的时候有没有报出来） |

全量 198 份并发跑（合同级 4 × 条款级 2）约 30 分钟，模型花费约 6 元——时间下限由本地检索决定，实测约 7.7 秒/份。上面三个数字都能用仓库里的脚本重算。

## 输出长什么样

下面是 `examples/` 里那份代言合同的真实结果（节选）：

```text
01_governing_law      存在 ✅   风险 中   置信度 0.95   证据 3
  理由：我方=CONSULTANT（顾问/被许可方，提供个人形象与代言服务并接收报酬的一方）。
        合同第25条明确约定适用堪萨斯州法律，第33条约定争议提交仲裁，管辖地完全位于对方
        所在地或与其紧密关联的司法辖区，缺乏中立性，增加了我方的维权成本与不确定性。
  缺口：建议争取将仲裁地改为中立城市或我方所在地，以降低异地维权的差旅与时间成本。
  证据 1｜原文位置 19173-19265
    This Agreement shall be governed and construed according to the laws of the State of Kansas.
```

完整样例（3 份合同 + 报告）在 `examples/`，看它**不需要 API key、不需要模型、不联网**。

## 怎么做的

一条固定流程，四步：

1. **切块与索引**：合同切成 1200 字符的小块（重叠 200），用本地 `bge-m3` 算成向量存进 Chroma；每份合同一个 collection，检索不跨合同。
2. **检索**：先向量粗召 20 段，再用本地 `bge-reranker-v2-m3` 精排，取前 5 段。
3. **判定**：把「这一类条款的判定标准 + 这 5 段原文」交给大模型，要求它输出固定结构的 JSON，并且**逐字照抄**原文当证据。
4. **校验与定位**：程序检查 JSON 是否合法、引用是否真的出自喂进去的那 5 段，并算出它在全文里的字符位置。

三个决定值得单独说：

**模型只负责照抄，位置由程序算。** 让模型直接报坐标，它报不准；而"看起来合理但位置是错的"证据比没有证据更麻烦——人不会去核对一个带精确坐标的引用。如果引用在喂进去的片段里找不到，就记成疑似幻觉、压低置信度，而不是编一个结论出来。

**只有"对方的错"才重试。** 模型输出格式不合格，就把错误回灌让它改；如果是我们自己代码的问题，直接抛出、不重试。这条是踩出来的：早期一个键名写错被当成"模型输出不合格"重试了两次，白烧 12 次调用，还把 bug 伪装成模型问题——报告格式完整、数字确定，只有拿标准答案核对才发现全错。

**把不确定的假设写出来。** 每条理由开头都必须先声明"我方 = 合同里的哪一方"。合同本身不标甲乙双方，这个假设不写出来就是隐形的，而且会漂移：实测同一份合同、同一模型、同一次检索结果，两轮结论不一致。

## 数字是怎么量的，以及它错在哪

评测集用 CUAD 的 198 份**官方纯文本**（不用 PDF 转换版——那版字符位置几乎全错，14.1% 的标注无法定位，会把"检索的问题"和"数据的问题"混在一起）。

逐类 F1：

| # | 01 | 02 | 03 | 04 | 05 | 06 | 07 | 08 | 09 | 10 |
|---|---|---|---|---|---|---|---|---|---|---|
| 条款 | 适用法律 | 控制权变更 | 转让限制 | 竞业限制 | 独家排他 | 终止通知 | 自动续期 | 责任上限 | 违约金 | 知识产权 |
| F1 | 0.986 | 0.756 | 0.986 | 0.821 | 0.683 | 0.847 | 0.835 | 0.918 | 0.541 | 0.796 |

做过两项改动，都做了受控 A/B（同批 30 份合同、同一个模型，每次只改变一项）：

| 指标 | 基线 | + 重排 | + 口径对齐 |
|---|---|---|---|
| 存在性 F1（微平均） | 0.854 | 0.879 | **0.889** |
| 精确率 | 0.867 | 0.852 | **0.889** |
| 召回率 | 0.843 | **0.907** | 0.889 |
| 证据定位准确率 | 0.912 | 0.929 | **0.938** |
| 必备条款缺失识别 | 0.935 | 0.826 | **0.957** |

重排在检索层的效果（全量 198 份，809 个查询）：hit@5 从 0.766 提到 **0.847**，MRR 从 0.607 提到 **0.737**，而 hit@20 不变——说明只是把已经召回的证据排到了前面。

**比分数更重要的是错误归因。** 把 300 条判定里判错的 31 条逐条查清：

| 判错 | 归因 | 数量 |
|---|---|---|
| 漏报 17 | 检索层：标准答案里的证据根本没被召回 | **14** |
| 漏报 17 | 模型层：证据已经喂给它了，还是判了不存在 | 3 |
| 误报 14 | 口径落差：我们的定义和 CUAD 的标注口径不一致 | **12** |
| 误报 14 | 待人工判定 | 2 |

真正的"模型错"只有 3 条（10%）。所以后面的投入放在检索和口径上，而不是换一个更强的模型。

## 已知局限

- 全量 198 份只有"改完之后"的数，没跑改之前的全量基线（预算限制）。所以增强效果用的是 30 份受控 A/B 加全量检索层指标，**不能拿 198 份和 30 份的数字直接相减**。
- 单次小样本有噪声：30 份重复跑大约有 ±2 个判定的波动。
- 标准答案不是真理，它只是"按另一套提问标出来的答案"。比如 CUAD 的 `Change Of Control` 问的是"什么构成控制权变更"，我们这一类问的是"合同里有没有针对它的安排"——同一句话可能一边算、一边不算。这是召回率上不去的主要原因，调模型解决不了。
- 三类条款目前偏弱：02 控制权变更误报多（30 个，占全部误报的 29%）、05 独家排他和 09 违约金漏报多（都是检索问题）。原因都已定位，修法写在 `badcase_log.md`。
- 输出还是 JSON + 终端 + 网页，没有 Word/PDF 导出，也没有人工复核界面。

## 怎么跑

**只看输出**（不用模型、不用 key、不联网）

```powershell
cd hetong
python -X utf8 examples/show_report.py --evidence
```

**网页版**（同样读本地已有报告，不调模型）

```powershell
python -X utf8 webapp/server.py        # http://127.0.0.1:8077
```

**完整跑一遍**（需要两个本地模型 + 一个 API key）

```powershell
# 依赖：先单独装 torch（指定 CUDA 版本），再装其余的
pip install torch==2.11.0 --index-url https://download.pytorch.org/whl/cu128
pip install -r requirements.txt
Copy-Item .env.example .env            # 填 API key 和两个模型的本地路径

# 数据集：CUAD 不会自动下载，从 github.com/TheAtticusProject/cuad 取
#   CUAD_v1.json -> data/cuad/CUAD_v1.json
#   full_contract_txt/ -> data/cuad/full_contract_txt/
python -X utf8 scripts/build_dataset.py
python -X utf8 scripts/build_index.py

# 审一份合同
python -X utf8 cli.py "LIMEENERGYCO_09_09_1999-EX-10-DISTRIBUTOR AGREEMENT" --show-evidence

# 跑评测（合同级 4 并发 × 条款级 2 并发）
python -X utf8 run_eval.py --tag baseline --jobs 4 --clause-jobs 2
```

`.env` 里几个开关：`LLM_PROVIDER` / `LLM_MODEL`（内置 dashscope、zhipu、ollama 三种，换供应商不动代码）、`RERANK_ENABLED`、`LLM_MAX_CONCURRENCY`（并发总闸）。

## 代码结构

```
clauses.py      10 类条款的判定标准（"考试大纲"的代码版）
schemas.py      输出契约：模型必须按这个结构返回
retriever.py    检索：向量粗召 → 交叉编码器精排
pipeline.py     主流程：组装 prompt → 调模型 → 校验 → 定位证据
run_eval.py     评测：三个指标 + 判错清单
cli.py          命令行入口
examples/       3 份合同 + 报告（离线可看）
webapp/         网页演示（只读）
scripts/        建数据集 / 建索引 / 检索层评测 / 归因 / 导出样例
eval/           评测集与全部指标 JSON
docs/           工程日志、工程版说明（含评测口径细节与路线图）
```

## 有意没做的事

- **没有用 LangChain / LangGraph。** 流程是固定的四步直线，不需要"会自己决策"的编排，也不想为此引入上百个依赖；重试、校验、证据定位这些恰好是核心，自己写反而更可控。等要做人工复核闭环（HITL）时再考虑。
- **没有把"换更强的模型"当解法。** 现在的瓶颈在检索召回和标注口径，换模型解决不了。
