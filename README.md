# 合同风险审查系统（MVP）

> 输入一份英文合同 → 输出**站在客户视角**的 10 类条款风险报告：每一条都给出「存在与否 / 风险档位 / 中文理由 / **原文证据的精确字符位置**」，并单独报警「必备条款缺失」。
> 全程可量化：所有结论都由**同一套评测口径**打分，能用一条命令复现。

```
┌─────────────────────────────── 全量 198 份合同的评测结果 ───────────────────────────────┐
│  存在性 F1      宏平均 0.817  |  微平均 0.878（精确率 0.873 / 召回率 0.884）             │
│  证据定位准确率  661/715 = 0.924   ← 引用的原文位置与金标准区间重叠                     │
│  必备条款缺失识别率  246/265 = 0.928                                                    │
│  0 剔除（PIPELINE_ERROR） / 0 失败  |  125.9 分钟 / 平均 38.2 秒每份  |  LLM 成本约 5~7 元 │
└────────────────────────────────────────────────────────────────────────────────────────┘
```

---

## 1. 它解决什么问题

法务/业务读一份几十上百页的英文合同时，真正要回答的是四件事：

1. 这 10 类**关键条款**里，哪些存在、哪些根本没人写？（**缺失比写得差更危险**）
2. 存在的那条，对我方（客户/买方）是保护还是陷阱？（风险高/中/低）
3. 依据是哪一句？—— 给**原文 + 字符位置**，而不是"我认为"。
4. 证据找不到时怎么办？—— **标记出来**，绝不编造。

产品形态上刻意做了两个取舍：

- **不生成法条解释**：只做"定位 + 判读 + 引证"，把解释权留给人；
- **不追求全自动**：低置信度的结论会被标成"建议人工复核"，评测时单独剔除。

huggingface-cli download BAAI/bge-reranker-v2-m3 --local-dir <模型目录>\bge-reranker-v2-m3

# ③ 配置（.env 已被 gitignore；没有 .env 也能跑 2.1 与 --help，不会崩）
Copy-Item .env.example .env

# ④ 建向量库（本地 bge-m3，不需要联网）

# ⑤ 审查单份合同（--show-evidence 打印证据原文与字符位置）

# ⑥ 批量评测（先自检，再跑；--resume 可续跑，中断不丢进度）

## 3. 架构与数据流

```
CUAD 数据集（198 份官方原始 txt）
   │  scripts/build_dataset.py → eval/golden_eval.jsonl（金标准：存在性 + 证据字符区间）
   ▼
切块（1200 字符 / 200 重叠）→ 本地 bge-m3 向量化 → Chroma（每份合同一个 collection）
   ▼
┌─ 检索层 ────────────────────────────────────────────────┐
│  向量粗召 top-20  →  cross-encoder（bge-reranker-v2-m3）精排  →  取 top-5   │
└─────────────────────────────────────────────────────────┘
   ▼
LLM 判定（每类条款一次调用）→ 强约束 JSON：exists / risk_level / confidence / reason_zh / evidence_quotes
   ▼
Pydantic 校验（只校验"模型该负责"的部分；不合格把错误回灌重试，仍不合格 → 打 [PIPELINE_ERROR] 标记）
   ▼
证据定位（**程序算位置**）：精确匹配 → 忽略空白匹配 → 全部失败 = 防幻觉信号（记入 gaps + 压低置信度）
   ▼
报告（JSON + 中文摘要）→ run_eval.py 打分（三个核心指标 + FP/FN 归因清单）
```

**为什么证据位置必须由程序算**：让模型"照抄原文"，位置我们自己找。这样"引用了一段原文"这件事是可验证的——找不到就是找不到，会变成一条明确的信号，而不是一段看起来很专业的幻觉。

## 5. 评测口径（全部写死在代码里，避免"每次算得不一样"）

| 指标 | 口径 | 为什么这样定 |
|---|---|---|
| **存在性 F1** | 逐类累计 TP/FP/FN/TN → 精确率 / 召回率 / F1；同时给**宏平均**（10 类等权）与**微平均**（汇总计数） | 宏平均暴露"小类被大类淹没"，微平均反映整体吞吐质量，两个都要看 |
| **证据定位准确率** | 分母 = 存在性判对的阳性 case；分子 = 其中证据与金标准**区间有重叠**的（模型没给证据 = 不命中） | 用"重叠"而非"完全相等"：实测模型常多带一个章节号前缀（`6.9 Governing Law.`），要求相等会误判为错 |
| **必备条款缺失识别率** | 分母 = 金标准为"不存在"的 01/08/10；分子 = 系统也判不存在 | 对审查工具而言"**漏报缺失**"是最危险的失败模式，必须单独度量 |
| `[PIPELINE_ERROR]` | **一律剔除、单独计数** | 管线自己崩掉的记录不能混进分数；更要紧的是：**绝不编造结论填坑** |

评测集：CUAD 的 **198 份官方原始文本**作主评测集（含 809 个正样本）；另有 510 份 txt 全集与 299 份 PDF 转换文本作鲁棒性集。

### 6.2 两项增强的前后对比（同批 30 份合同，唯一变量＝增强开关）

| 指标 | 基线 | + 重排 | + 口径对齐 |
|---|---|---|---|
| 微平均 F1 | 0.854 | 0.879 | **0.889** |
| 微精确率 | 0.867 | 0.852 | **0.889** |
| 微召回率 | 0.843 | **0.907** | 0.889 |
| TP / FP / FN | 91 / 14 / 17 | 98 / 17 / 10 | **96 / 12 / 12** |
| 必备条款缺失识别率 | 0.935 | 0.826 ⚠️ | 0.957 |
| 证据定位准确率 | 0.912 | 0.929 | **0.938** |

**增强①**　重排（粗召 20 → cross-encoder 精排 → 喂 5 段，prompt 不膨胀）
　　检索层全量 198 份实测：**hit@5 0.766 → 0.847（+8.1pp）、MRR 0.607 → 0.737（+13.0pp）、hit@20 不变**（证明只改了排序、没偷用额外召回）。
　　端到端收益是**召回 +6.4pp**（漏报 17→10）；代价是精确率略降——检索喂进来的相关文本变多后，模型也"发现"了更多按我们标准算命中、但金标准不认的条款。

**增强②**　口径对齐 v0.9.4（两处，均依据真实误报 case）
　　· §8 责任上限：只认**一般性**上限；绑定特定情形的额度限制/免责不算。
　　· §10 知识产权：改看「**有没有归属/转让的动作**」（`assign` / `transfer` / 记录义务），而不是"标的是否为新成果"——这正是本项目铁律「**看动作，不看词**」在该类上的落地。
　　结果：目标类逐条核对通过（08 误报 2→0、10 误报 6→0、误伤 3 个全部收回），10 类 F1 0.750 → **0.875**。

### 6.3 判错归因（自动生成，零 LLM 调用）

对 30 份 / 300 条判定中的 **31 个错误**逐条归因（见 [badcase_attribution.md](badcase_attribution.md)）：

| 判错类型 | 归因层 | 数量 | 占比 |
|---|---|---|---|
| 漏报 17 | **检索层**（金标准证据根本没被召回） | **14** | **82%** |
| 漏报 17 | 模型层（证据已召回，仍判不存在） | 3 | 18% |
| 误报 14 | **口径落差**（我们的定义 vs CUAD 标注不一致） | **12** | **86%** |
| 误报 14 | 待人工判定 | 2 | 14% |

> **31 个错误里，真正的"模型错"只有 3 个（10%）。** 其中检索失败不是"差一点"：归因表里"最近片段相距"高达 2204 / 5900 / **10986** / **13222** / **21518** 字符。
> 这条结论直接决定了后续投入方向：**修检索和口径的收益远大于换模型**。

## 7. 已知局限（必须一起读）

1. **全量 198 份只有"增强后"的数，没有全量基线**（受预算限制）。因此"增强效果"的证据是：**同批 30 份受控 A/B**（唯一变量＝增强开关）+ **全量 198 份的检索层对比**。**不能**把"198 份的 0.878"与"30 份的 0.854"直接相减当作增强效果。
2. **单次小样本存在噪声**：实测同模型、同配置、同数据重跑，30 份的波动约 **±2 个判定**（微 F1 约 ±0.02）。纪律：小样本只认"**目标类逐条核对**"，整体指标要么跑全量、要么重复取均值。
3. **金标准不是真理**，它只是"按另一套提问标注的答案"。例如 CUAD 的 `Change Of Control` 问的是"**什么构成**控制权变更"，我们的第 2 类问的是"合同里有没有**针对**控制权变更的安排" —— 同一句话可能一边算、一边不算（实测已捕获金标准自相矛盾的成对 case）。这类**口径落差**是召回率上不去的结构性原因，只能记录、不能靠调模型解决。
4. **三类短板有明确原因**：`02` 误报 30 个（占全部误报的 29%，属口径落差族，是下一个待修目标）；`05` / `09` 漏报多（检索层问题，需改造查询构造，`09` 还存在 `penalty` 与 `liquidated damages` 的字面差异）。
5. **报告输出仍是 JSON + 终端表格**，没有 Word/PDF 导出；**没有人工复核界面**（HITL）。
   ~~单份审查串行~~ → 已完成**并发改造（工程增强 E1）**：合同级 × 条款级并发 + LLM 并发总闸 + GPU 检索串行，
   全量 126 分钟 → **约 30 分钟**（下限由串行检索决定：7.7s/份 × 198 ≈ 25 分钟）。
   该改造**不改变任何判定结果**，并已用"桩对象 + 变异检验 + `--resume` 端到端对比"三层零成本验证，见 `docs/工程日志.md` §8。
6. **E1 的真机计时待补**：约 30 分钟是按"检索 25 分钟 + LLM 并发尾巴"推算的**预期值**，实测需要真实 LLM 调用（约 0.3 元）。

## 8. 踩过的坑（工程教训，按价值排序）

| # | 现象 | 教训 |
|---|---|---|
| 1 | 一个 `hit["id"]` 键名错误（正确是 `chunk_id`）被当成"模型输出不合格"重试，**烧掉 12 次调用**，还把真实 bug 伪装成 `[PIPELINE_ERROR]` —— 报告显示"10 类条款全部缺失"、格式完整、数字确定、还付送了缺失报警 | **「能跑通」≠「结果可信」**。不拿金标准核对，这个错误会一路带进评测分数里而且永远发现不了 |
| 2 | 同上 | **只有"对方的错"才值得重试**：模型输出不合格 → 回灌错误让它改；我们自己的 bug → 直接抛出，绝不重试 |
| 3 | 我曾把 03 类的风险档归因为"标准缝隙"，加了"立场显式化"后才发现真因是 prompt 里"我方是谁"不可审计（同一合同、同模型、同检索，唯一变量是 prompt，结论却从 `low` 漂到 `high`） | **归因本身也要被质疑**。归因错了，就会去修错的东西（差点改掉没问题的标准）。后续所有分歧都按「管线层/检索层/模型层/标准层/数据层」五选一强制归因 |
| 4 | 我依据旧记录断言"本机 torch 是 CPU 版"，实测是 `2.11.0+cu128`、CUDA 可用；而且是我自己在 `.env` 里写了 `RERANK_DEVICE=cpu` 把它按在 CPU 上 | **环境类事实必须实测**。改 `auto` 后：单次检索 **10.10 秒 → 0.81 秒（13 倍）**，且逐类逐指标与 CPU 版完全一致（顺带验证了可复现性） |
| 5 | `.env` 里是 `CHUNK_MAX_CHARS`，代码读 `CHUNK_SIZE` | **静默失效**：不报错，只是指标里记成 `chunk=?`，悄悄丢信息。指标元数据必须与配置键名对齐 |
| 6 | 两份超长合同名截断后**撞成同一个报告文件名** | 比"丢一份报告"更危险的是：`--resume` 会把 A 的报告当成 B 来打分 → **指标被悄悄污染**。文件名清洗必须带防碰撞哈希 |
| 7 | 长跑评测被"无输出超时"杀掉（用了 `Select-Object -Last N` 把输出缓到结束） | **长跑任务要让输出实时流式打印**；并且把「LLM 调用（贵/慢）」与「打分（快/免费）」分离——`--resume` 读磁盘报告重新打分，几秒出结果 |
