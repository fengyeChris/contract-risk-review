# examples —— 离线样例（零模型、零 API、零向量库）

## 这是什么

3 份真实合同 + 它们跑出来的审查报告。**不需要装模型、不需要 API key、不需要向量库**，
一条命令就能看到系统输出长什么样：

```powershell
cd hetong
python -X utf8 examples/show_report.py --evidence
```

## 三份样例分别展示什么（不是随便挑的）

| 合同 | 类型 | 与金标准的差异 | 看点 |
|---|---|---|---|
| `LIMEENERGYCO … DISTRIBUTOR AGREEMENT` | 经销协议 | **9/10 一致**（04 竞业限制误报） | 正常路径：必备条款缺失报警正确（08 责任上限、10 知识产权） |
| `ADAMSGOLFINC … ENDORSEMENT AGREEMENT` | 代言协议 | **9/10 一致**（02 控制权变更误报） | **"知道自己哪里错"**：这条误报正是 badcase 日志里那 19 个"**转让条款被判成控制权变更**"的典型 —— 模型引用的证据居然是章节标题 `31. ASSIGNMENT AND CHANGE OF CONTROL` 本身；修复方案已写明（BC-007），只是还差 1 元验证预算 |
| `PfHospitalityGroupInc … Franchise Agreement` | 加盟协议 | **7/10 一致**（05 误报、06/07 漏报） | 诚实面：长合同（149KB、证据 21 条）上错误更多，且三类错误分属不同层（检索/口径） |

> **不挑"全对"的样例来展示**，是刻意的：这个项目真正的能力不是"跑出分数"，
> 而是**知道每个错在哪一层、该怎么修、要花多少钱验证**。样例里保留错误反而是证据。

## 为什么报告里会有"字符位置"

这是本项目的核心设计：**模型只负责逐字照抄原文，字符位置由程序在检索到的片段里查找计算**。

所以每个证据都带 `char_start / char_end`，可以用它把原文精确切出来 ——
`show_report.py` 就在**当场校验**这件事：按位置切出来的那一段，必须与报告里存的原文完全一致
（三份样例当前全部 `一致 ✅`）。

> 为什么不让模型直接给位置？因为它给不准，也不该让它猜。而"看起来合理但实际错位"的证据，
> 比没有证据更危险 —— 人不会去核对一个带精确坐标的引用。

## 一个能直接看出来的模型问题

翻到 `ADAMSGOLFINC` 那份报告会发现：**10 类条款里有 9 类把"我方"声明成了 `CONSULTANT`（代言人）**，
而 09 类又写成 `ADAMS GOLF`。按项目口径，"我方 = 支付价款并接收产品或服务的一方" ——
**代言人是收款方，自相矛盾**。

这不是 bug，而是「立场在合同里没有标注」时的真实困难。项目为此做了两件事：
① prompt 里**强制第一步先声明"我方=谁"并写在理由开头**（假设从隐形变可审计）；
② 归因时把这类问题归到**模型层/prompt 层**而不是标准层 —— 见 `badcase_log.md` BC-004
（这条归因曾经错过一次，差点改掉一个没问题的标准）。

## 数据来源与许可

- 合同原文来自 **CUAD**（*The Atticus Project* 的 Contract Understanding Atticus Dataset），
  许可 **CC BY 4.0**，允许在署名前提下再分发。
  项目用的是 CUAD 的**官方纯文本**（不是 PDF 转换版 —— PDF 转换文本的字符位置几乎全错，
  实测 14.1% 的标注无法定位，所以主评测集只取官方文本）。
- 报告 JSON 由本项目生成。生成参数：`qwen3.8-flash` / `temperature=0` / 重排开
  （粗召 20 → 精排取 5）/ `chunk=1200-200` / 立场 = customer。
  原始产物在 `data/`（体积大、不进版本库）。

## 重新生成

```powershell
python -X utf8 scripts/build_examples.py     # 从 data/ 重新导出（需先跑过 run_eval.py）
```

脚本会先校验三份样例的原文与报告**都在**，再开始复制 —— 避免中途失败留下"看起来完整的半成品"。
