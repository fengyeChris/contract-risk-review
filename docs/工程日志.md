## 0. 项目一句话

用**朴素向量 RAG**（切块 → embedding → top-k 检索 → LLM 按 schema 输出）审查英文商业合同，逐类检查 **10 类风险条款**，输出「是否存在 / 原文证据及字符位置 / 风险等级 / 置信度 / 缺失必备条款」。
数据：CUAD（510 份真实商业合同，41 类人工标注）。**风险判读立场固定为「客户 / 买方视角」。**

## 4. 踩坑记录

### 坑 1：CUAD 里根本没有"赔偿条款"标签

- **现象**：准备写映射表时核对类别名，发现第 9 类的金标准不存在 → 该类 F1 永远算不出来。
- **定位**：直接对 20,910 条标注做集合运算，41 个类别名中**不含** `Indemn`。
- **根因**：规格（10 类）是"想做的"，数据（41 类）是"能做的"，两者未必对齐。
- **解决**：口径变更为**违约金（Liquidated Damages）**，并**同步更新四处**：`mvp_scope.md` 条款 9 整章、`ClauseId` 枚举、必备清单（4 类 → 3 类）、测试用例；原项记入 backlog。
- **可迁移规则**：**先核对数据，再写代码。** 规格可以被数据修正，但修正必须留痕、必须同步所有引用点。

### 坑 2：PDF 转换文本的字符位置几乎全错

- **现象**：官方文本的位置精确率 ~100%，PDF 转换文本几乎为 0。
- **根因**：PDF 提取会把换行、空格、连字符带进文本，`answer_start`（官方文本的字符下标）整体错位。
- **解决**：① 三级定位（精确 → **忽略空白重新定位**并按下标映射还原 → `unlocatable`）；② **分数据集**：位置可信的 198 份才算定位指标；③ 把"5.8% 证据无法被单块完整包含"反馈到 Step 4 的指标定义（context recall 必须按**检索结果集合**算）。
- **可迁移规则**：**指标的分母必须干净**；不同质量的数据不能混进同一个指标。

### 坑 3：文件名特殊字符导致 4 份合同漏匹配

- **现象**：正样本统计比预期少 1 个 —— 而且是**用户报的 61 纠正了我的 60**。
- **根因**：`A/R`、`MACY'S` 这类字符在不同来源里写法不同，单一的空白归一化匹配不上。
- **解决**：两级归一化 key（只保留字母数字 → 再激进地删掉全部标点）+ 逐级回退查找；修完 510/510 全匹配。
- **可迁移规则**：**交叉验证**比单点统计可靠；归一化要准备"更宽松"的一档。

### 坑 4：本地模型缺 `1_Pooling/config.json` → **静默**退化为 mean pooling

- **现象**：不报任何错、程序正常跑完，但检索质量会悄悄变差。
- **根因**：`SentenceTransformer(目录)` 在缺少 pooling 配置时默认用 mean pooling，而 **BGE 系列必须用 CLS pooling**。
- **解决**：显式 `Pooling(dim, pooling_mode="cls")` 并打印核对；同时**主动说明**：最初设计的"自检索 distance=0"检查**根本测不出 pooling 对不对**（同一文本无论何种 pooling 都是同一向量）。
- **可迁移规则**：**不报错的错误最贵**；并且要清楚**每个测试能测到什么、测不到什么**。

### 坑 5：`sentence-transformers 6.1` 的 API 变更

- **现象**：`AttributeError: 'Pooling' object has no attribute 'pooling_mode_cls_token'`。
- **解决**：先用 `inspect.signature(Pooling.__init__)` **查签名**，再按新 API 写（`pooling_mode="cls"`）；同时保留旧模块路径 fallback 以兼容旧版本。
- **可迁移规则**：**不猜 API**，先查签名/文档再写。

### 坑 6：进度显示的分子分母不同源

- **现象**：后台日志出现 `索引整体 27745/19616` —— 分子比"本数据集总量"还大。
- **根因**：两个数据集共用一个 collection，代码用 `collection.count()`（全量）当分子、`len(chunks)`（本 split）当分母。
- **解决**：拆成两个量——"全量已有 id"用于增量差集，"本 split 已有条数"用于进度显示；并把"单 collection + metadata"的设计与注意事项写入工程约定。
- **可迁移规则**：**统计口径必须写清楚**，分子分母要同源。
- **后续复盘（同一个坑犯了三次）**：修完"进度显示"后，我没有顺手检查"还有哪些地方引用了同一个指标"，结果 30 分钟后**自检 ①** 又用 `collection.count()` 当分子，再次误报失败（`32873 / 预期 19616`）。
  → **补一条更硬的规则**：修"统计口径"类 bug 时，必须**搜索所有引用该指标的位置、一次过完**（例如全局搜 `collection.count()`），否则就是打地鼠。这条与坑 7 的"修根因不只修症状"同源——我也犯了第二次，区别是这次靠**交叉验证**（分 split 统计）在 1 分钟内抓了出来。

### 坑 7：U+2028 + `splitlines()` 把 JSONL 记录切断（最有价值的一个）

- **现象**：`json.decoder.JSONDecodeError: Unterminated string starting at line 1 column 205`（只在鲁棒性集上出现）。
- **定位过程**：
  1. 读 traceback → 追问"`line 1` 指的是**文件第一行**，还是**交给 json 解析器的那段文本**的第一行？"
  2. 判断出是"**切行**"这一步的问题；
  3. 写诊断命令：打印出错位置 `repr` + `splitlines()` 与 `split("\n")` 的行数对比 + 控制字符统计；
  4. 得到铁证：`splitlines()` 多切 **16** 行；文件里有 **U+2028（LINE SEPARATOR）×17**。
- **根因（两层，缺一不可）**：
  - `json.dumps(..., ensure_ascii=False)` **不会转义** U+2028（JSON 规范允许字符串里未转义它）；
  - `str.splitlines()` 会按 **10 种字符**断行（`\n \r \v \f \x1c \x1d \x1e \x85 \u2028 \u2029`），而 **JSONL 的"行"只应由 `\n` 定义**。
- **解决**：在 `text_utils.py` 提供**唯一**的 `read_jsonl()`（按文件对象迭代，只认 `\n`）与 `write_jsonl()`（写完后**自检文件行数 == 记录数**）；全项目 **4 处**调用点统一替换；顺手清掉重构后失效的 import。
- **可迁移规则**：① **用专门的函数读专门的格式**（通用字符串方法不懂格式规则）；② **修根因不只修症状**（另外 3 处都是定时炸弹）；③ **让错误在写入端暴露**；④ 这个坑只在脏数据集上暴露——**鲁棒性集的价值实证**。

### 坑 8：CPU 嵌入要 67 分钟

- **现象**：bge-m3 在 CPU 上 3.3 条/秒，全量 13,257 chunk 需约 67 分钟，迭代太慢。
- **解决**：① **先测速不猜**，并做 batch_size 调优（8 最优，16/32/64 反而更慢）；② 核实官方索引里**确实有**匹配 Python 3.13 的 `cp313 + cu128` Windows 轮子（不凭印象）；③ 下载 2.56 GB 后 **SHA256 校验**；④ 替换安装 → 验证 `cuda_ok=True` → 重测（**13.5×**）；⑤ 记录回滚命令。
- **可迁移规则**：**性能问题先量化再优化**；大文件必须校验哈希；改共享环境要**可回滚**。

### 坑 9：多处规格与现实偏差

- 198 份 vs 规格写的 50~100 份；无训练集、也不切 dev 集；embedding 由 `bge-small-en` 改为 `bge-m3`；reranker 被主动推迟。
- **解决**：每一处都**显式记录理由**（写入 `mvp_scope.md` 对应小节）并**记入 backlog**，绝不留"偷偷改了"的地方。
- **可迁移规则**：**规格可以调整，但要留痕**——面试时"我为什么改"比"我按规格做了"更有说服力。

## 5. 贯穿全程的四条方法论

1. **先量化，再决策**：chunk 参数、overlap、top-k、嵌入速度、位置错位率——全部先测真实数据。我们甚至用实测**推翻了自己的直觉**（overlap 60→365 只换 0.3% 覆盖，成本却 +6.4%，最终选 200）。
2. **标准先行，代码跟随**：`mvp_scope.md` 是唯一真相源。改口径 = 同步改「标准文件 + schema + 测试 + 映射表」，四者缺一不可。
3. **指标的分母必须干净**：分数据集、"不可定位"样本排除出定位指标、"单块覆盖"与"检索结果集合覆盖"要分清——否则归因会指向错误的地方。
4. **让错误尽早暴露，并知道测试测不到什么**：写入自检、schema 校验、自检索检查、双维度进度；更重要的是能指出"这个测试证明不了什么"。

> "加载本地 BGE 模型时一切正常、不报错，但检索质量会悄悄变差——因为模型目录缺少 `1_Pooling/config.json`，`sentence-transformers` 默认用了 mean pooling，而 BGE 必须用 CLS pooling。

## 8. 工程增强 E1：并发化（126 分钟 → ~30 分钟）

> **编号说明**：用独立编号 E1，**不占用 AGENTS.md 的 Step 5.x**。那一套是"会影响指标"的增强
> （5.2 混合检索 / 5.3 重排 / 5.4 查询改写…），而并发化只改速度、**不改任何判定结果**。
> 混在一起会让"哪次改动影响了分数"永远说不清。

### 8.1 三类资源必须分开设限（本次最重要的一条）

只设一个"并发数"一定会出事。落地做法是把资源拆成三类分别处理：

| 资源 | 策略 | 实现 | 为什么 |
|---|---|---|---|
| 网络（LLM） | **可并发，但必须设总闸** | 模块级 `_LLM_SEM = Semaphore(LLM_MAX_CONCURRENCY)`，包在 `call_llm` 的请求体外 | 低价/免费档有并发与 QPS 限制；无上限只会换来一堆 429，再靠退避重试把时间还回去（**比串行还慢**）。总闸全局共享 → "合同级 × 条款级"无论怎么组合都突破不了 |
| GPU（向量化 + 重排） | **必须串行** | `_GPU_LOCK` 包住 `retrieve_for_clause` | 一块卡上两个前向互相抢显存/算力；检索约 0.77s/类，串行代价小，换来结果稳定 |
| 标准输出 | 加锁 | `_emit()` + 进度计数锁 | 多线程 print 会互相插字，日志读不了 |

### 8.2 结果顺序：并发改造最容易踩的坑

- `review_contract` 用 `ThreadPoolExecutor.map`（**按提交顺序返回**），不用 `as_completed`。
  报告与评测都按顺序读 `findings`，顺序一错就与金标准错位 —— **这类 bug 不崩溃，只会让分数不可信**（比崩溃更危险）。
- `run_eval.py` 拆成两阶段：**并发生成报告** + **主线程串行打分**。
  打分不进线程池：多线程往同一份 metrics 里累加 = 结果不可复现，而打分几乎不耗时 ——
  那是拿"确定性"换毫秒，亏本。
- 串行模式（`--jobs 1`）的输出格式**保持与改造前完全一致**，避免"改进"顺手改坏既有工作流。

### 8.4 收益与**下限**（诚实版）

- 单份审查：38s → **约 12~15s**（检索 7.7s 串行 + LLM 并发；真机计时待补，见下）。
- 全量 198 份：126 分钟 → **约 30 分钟**（**不是** 20 分钟）。
- **下限由串行检索决定**：7.7s/份 × 198 ≈ **25 分钟**。想更快只能动检索（降 `RERANK_CANDIDATES`、换小模型），
  而那会改变检索质量 —— **不做**（要改也得先有同口径 A/B 证据）。
- ⏳ 端到端真机计时验证需要真实 LLM 调用（2 份合同 ≈ 0.3 元），**待有预算时补**；
  在那之前，"约 30 分钟"是按"检索 25 分钟 + LLM 并发尾巴"推算的预期值，不是实测值。
